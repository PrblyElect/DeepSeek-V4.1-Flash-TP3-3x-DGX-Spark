# FIXLOG — ds41-flash-tp3 (V4.1-Flash on 3× DGX Spark, vLLM b12x)

Every failure mode encountered during bring-up, its root cause, and its
fix. Roughly ordered by when each failure was met on the road to first light (boot-fatal modes first).

| # | Symptom | Root cause | Fix |
|---|---|---|---|
| 1 | Head node kernel-OOM during weight load; workers survive | NCCL connection buffers pin ~4.7 GiB unreclaimable host RAM per node; the head (carrying the API server and the usual daemons) has ~2 GiB less margin than workers | `NCCL_BUFFSIZE=1048576`, `NCCL_LL128_BUFFSIZE=262144`, `NCCL_PROTO="^LL128"` — cuts pinned to 139 MiB |
| 2 | Kernel-OOM ~7 s into load with only 1.4 GiB process RSS | Engram tables staged into host memory (~31 GiB/rank) on top of 95 GiB weights | `--engram-config '{"cpu_offload":false,"table_memory":"disk"}'` |
| 3 | Head node OOM at ~4 min into load (repeats identically across 4 boots) | The b12x O_DIRECT loader's pinned bounce buffers add 10–16 GiB unreclaimable host memory during weight loading | `--load-format safetensors` (kernel-evictable page cache instead of pinned buffers) |
| 4 | `ValueError: Free memory on device cuda:0 less than desired GPU memory utilization` | The fork checks free memory at startup against gmu × total; busy head node has less free than clean workers | gmu 0.85 (not the fork default 0.92); run `echo 3 > /proc/sys/vm/drop_caches` before boot — the shipped launcher and `ds41-flash-tp3-up` attempt this drop automatically (best-effort, passwordless sudo) |
| 5 | `io_uring bounce initialization failed: Operation not permitted` | Docker's default seccomp profile blocks io_uring syscalls used by the b12x I/O layer | `--security-opt seccomp=unconfined` |
| 6 | `AssertionError: 129280 is not divisible by 3` | V4.1's vocabulary (129,280) is not divisible by 3. The assertion is not in the pinned build — the only vocabulary-divisibility check in this image is in the b12x ngram-embedding path, and it divides a padded vocabulary — so the requirement is settled by posture rather than by a mechanism readable in the shipped build | Serve a single `--served-model-name main`; the fork runtime-pads attention heads, o_groups and drafter experts automatically, and the boot gate proves the model directory is the natural pull |
| 7 | Spec-decode boots OOM'd at every gmu/KV combination tried | Initially read as capacity. The complete six-boot matrix reattributed it: the early deaths were the **kernel tuners**, not the drafter — the b12x autotune arena self-budgets at half of free memory, and the fork's FlashInfer autotuner is a second independent surface. With both disabled (`B12X_AUTOTUNE=0` + `--no-enable-flashinfer-autotune`), a spec boot at a reduced KV pool allocates the pool, captures its CUDA graphs, and **serves** — see failure mode 10 for the wall that remains | Superseded by failure mode 10 |
| 8 | `expandable_segments:True` produces NaN logits on >64-token prompts | GB10 unified memory + PyTorch's expandable segments allocator interact badly | `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False` (mandatory) |
| 9 | Raising the chunked-prefill batch width to 16384 killed BOTH worker ranks during the b12x compile phase, while the head node's worker survived — the triangle came back healthy only after reverting to 8192 | Larger batch shapes create new b12x compile candidates, and the compile-time memory spike exhausts unified memory on the workers before any serve-time memory check runs; the startup free-memory gate evaluates a config-time snapshot and does not cover compile shapes. The kernel log on a dead worker shows the generic signature: `Out of memory: Killed process ... (VLLM::Worker_TP)` followed by an NVIDIA `NV_ERR_NO_MEMORY` from the unified-memory allocator | Keep the shipped 8192 — the launcher's `MAX_NUM_BATCHED_TOKENS` (MNBT — max num batched tokens) knob carries this warning inline. A retest requires a memory plan: reduced `GMU` for the boot window, a post-weight-load available-RAM check on every box (the config-time snapshot is not the serve-time state), and the b12x reader's own block counters surfaced so the effect is measured. Forensics note: plain `dmesg` is permission-denied on these boxes — `sudo -n dmesg -T` works, and its stamps are the box's LOCAL time, not UTC, so kernel timestamps and engine logs disagree by the box's UTC offset |
| 10 | The first serving spec-decode boot: pool allocated, CUDA graphs captured, health 200 — then the HEAD rank was kernel-OOM-killed roughly a minute into its first deep-context prefill (a few hundred K tokens), at the best knob-accessible pool (2.3 GiB KV, both tuners off) | The drafter's ~3 GiB/rank residency leaves the head unable to absorb the **deep-prefill memory transient** — the failure is steady-state and workload-shaped (exactly the RAG traffic this recipe serves), not boot-phase. Smaller pools cut concurrency toward the 50% line without adding transient headroom, and the failure being a prefill spike means per-sequence buffers are not the lever | Spec decode **REJECTED, final** — a **capacity** verdict, not a stability one (a later re-test, 2026-11: with the KV-capacity overlay and both tuners off, this same 2.3 GiB pool **serves** deep prefills — 2×512K verified at a ~1.7 GB trough — so the first-prefill OOM above was that boot's stack, not a permanent wall; the rejection stands because the spec pool is ~2.1M tokens against the shipped ~5.1M). Reopening at full capacity requires more memory per rank (a 64 KiB-page kernel with the memory saver, the display carve-out) or a *trained* smaller drafter — engine/OS projects, not flags. The zero-weight alternative (n-gram prompting off the request's own tokens) is untested here and is the only spec-adjacent direction that does not carry the drafter's residency |
| 11 | Some boots kernel-OOM-killed a worker during the b12x compile phase at the SHIPPED batch width — intermittent, and deeper on aged boxes | The autotune benchmark arena self-budgets at **half of free memory**; on this unified-memory kernel `MemAvailable` can read zero, so nothing self-limits it. Disabling benchmarking removes the entire arena | `B12X_AUTOTUNE=0` is now the shipped default: heuristic kernel plans ship as prebuilt cubins — boots run in roughly half the tuned time, decode speed is unchanged (measured), and the cost is a one-time cold-prefill penalty of a few percent per new document (prefix-cache hits are unaffected). The fork's separate FlashInfer autotuner benchmarked zero configurations on this model and is disabled in the shipped launcher (boot hygiene, not a speed lever) |
| 12 | A short request's first token landed only after a concurrent deep prefill finished entirely — tens of seconds of queueing at the shipped batch width, measured directly with a paired probe (short request fired into a ~350K-token prefill) | One prefill runs at a time by default (`max_parallel_prefills = 1`): the new request's tokens queue behind the long prefill's chunks | `--max-parallel-prefills 2 --prefill-policy decode-aware`, shipped as `PAR_PREFILLS`/`PREFILL_POLICY`: the paired probe reads **single-digit seconds** beside the same deep prefill (under five at the shares of that era; ≈5–6 s at the later shipped 0.2 — failure mode 16), with the long prefill itself unaffected (within noise) — the shared chunk budget absorbs the small prefill in the big one's inter-chunk gaps. The engine rejects the policy when the count is 1, so the launcher passes the pair only above 1 |
| 13 | Raising `--max-model-len` to 1M appeared to grow the KV pool (the engine's token figure moved from ~2.4M to ~3.1M tokens) "for free" | Accounting, not capacity (on the stock accounting, before the row-15 overlay): the pool's byte reservation and block count are fixed by `--kv-cache-memory-bytes`; the reported token figure scales with the context value at the same blocks | Adopted at 1M — one full 1M request fits in the pool, and deep-prefill admission is verified to ~900K at the shipped batch width (later re-tested, 2026-11: two full-1M prefills admitted concurrently and served clean at a ~2.1 GB trough — the accounting note stands, and the full-context admission is no longer untested). When comparing pools across context values, quote the **block count**, not the token figure |
| 14 | Swapping the MoE backend to the b12x family looked forbidden: its tiny-decode path drops the model's clamped-SwiGLU limit on small-batch decode with no error signal | The hazard is real but it is a PATH, not the backend: with the tiny-decode kill switch on (`B12X_W4A8_TINY_DECODE=0`), the general kernel runs and receives the clamp through the normal plan chain. The backend itself is family-120-capable and clamp-aware on that path | Adopted as the shipped default (`MOE_BACKEND=b12x` + the kill switch, both launcher-forwarded): ~31 tok/s solo decode (up from the ~29 band), clean four-stream concurrent parity, prefill at the top of its band, no memory cost. One posture-specific quirk: vision requests emit a short run of invisible completion tokens before the answer — budget `max_tokens ≥ ~200` for vision. The verifier now asserts the kill switch's resolved value on every run |
| 15 | The startup line claimed ~3.1M tokens at 1M context (69% of the pool's physical slot capacity); the community's identical-hardware lane claimed 5.5M from the same 256-token block geometry | The stock capacity figure charges EVERY request its 15 sliding-window groups' worst-case span — the window plus one whole batched-token budget per in-flight step (the unsettled batches are a system-wide quantity, not per-request). Ported the steady/transient split (the class of open upstream PR vllm-project/vllm#52495): each request pays its window+lookahead; the unsettled batches are charged once to the pool | Shipped as a two-file overlay (`launch/tp3-kit/overlay/`) installed by the bootstrap before the boot gate (the manifest pins the patched hashes): the pool figure rose to ~5.1M tokens / ~4.9× at 1M from the same 5 GiB reservation, and the full-sequence admission gate flag (`--no-scheduler-reserve-full-isl`) is pinned so multi-request admission actually uses it. Seven concurrent 512K prefills (3.6M tokens resident) verified |
| 16 | A short request **decoding** while a deep prefill churns ran at ~1.4 tok/s — a plain sentence took the better part of a minute — while the same request on an idle lane decoded at full speed; mixed-step token caps (`--max-num-scheduled-tokens`) did nothing | The scheduler alternates pure prefill-only and decode-only steps at this parallel-prefill count, so a cap on mixed steps never binds: the decode step waits behind every prefill chunk with no guaranteed compute slice | A static decode-under-prefill share plus a contended-prefill token cap (`--prefill-compute-share` + `--max-num-prefill-tokens-per-step`), shipped as `PREFILL_COMPUTE_SHARE=0.2` + `PREFILL_TOKENS_PER_STEP=2048`. The measured ladder (paired, phase-locked, capability-clean at every rung): ~1.4 → ~8–10 tok/s at 0.5, ~22 at 0.3, **~25 at the shipped 0.2** — at zero idle cost, with the deep prefill's wall flat at the 0.3/0.2 rungs (+2–11% at the first 0.5 rung), buying a short-request TTFT of ≈5–6 s versus ≈4.6–4.8 s at the higher shares (+~7%, settled by paired same-boot A/B comparisons against a concurrent control; the whole 95% interval inside the +25% ceiling the trade was measured against). `PREFILL_COMPUTE_SHARE=""` in the launcher's environment restores the legacy scheduler |

## Failures in the bring-up path itself

These are defects in the recipe's own scripts, not in the serving stack —
they were found by re-running the published quick start end to end. If
you are on an older copy, expect them.

| Symptom | Root cause | Fix |
|---|---|---|
| `./launch/ds41-flash-tp3-up: Permission denied` | The launcher was published without the executable bit, so the quick start could not start | Published with mode 755 |
| `preflight failed on <box>` on the first box, every time, with `MISSING: checkpoint not staged` | The checkpoint check expanded `$(source "$ENV_SRC" ...)` on the BOX, where `ENV_SRC` is unset, so the path was empty and the test could never pass | Resolve every value on the operator's side, inject it as a literal, and let the box use its own variables |
| `preflight` never warned about memory | The `free -g | awk` field reference was written `$$7` inside a double-quoted ssh payload, so `$$` expanded to the operator's shell PID on the sending side and the box received a literal `PID7` instead of `$7` — the comparison never matched | `\$7`, so the box compares field 7 |
| `preflight` accepted any image named `eugr/spark-vllm-b12x:nightly-20261015` | The check compared the tag string only; a moved tag passes | The preflight now asserts the manifest digest AND the sha256 of the image's RootFS layer list |
| `start` failed with `bash: start-tp3-fork.sh: No such file or directory` | The launcher called a script the recipe did not ship, and `stage-env` copied only `cluster.env` | The recipe now ships `launch/start-tp3-fork.sh` and `launch/tp3-kit/`, and `stage-env` copies both to every box |
| `stage-env` failed with `No such file or directory` | The remote target directory was never created | `stage-env` creates the layout on each box first |
| Edits to `config/cluster.env` (KV pool, block size, max-num-seqs, parsers, loader) were silently ignored, and the served line did not match the file | The launcher never forwarded those knobs into the container, so the engine always ran the built-in defaults | The knobs are forwarded into the container explicitly, and the served line can be read straight off the command the launcher runs |
| The engram configuration in `config/cluster.env` had no effect, and the value the launcher held could pick up a stray `}` once it was actually passed through | The value was never forwarded into the container, and its default sat inside a `${VAR:-...}` expansion — where a `}` ends the expansion early as soon as the variable is set, so the value was correct only while nothing set it | The default is assigned in two steps with a single-quoted literal, on the host side and again inside the container, so the profile's value is passed through unchanged |
| `RAM-PROBE FINAL min_available_kb=0` on a box with several GiB free | The probe sampled `MemAvailable`, which reports 0 on this unified-memory kernel even when memory is available | The probe measures reclaimable headroom instead (free + reclaimable slab + reclaimable page cache) and keeps the minimum across the boot; `MemAvailable` is still reported beside it so the discrepancy stays visible |
| The served model name stayed `main` even after `SERVED_MODEL_NAME` was changed in `config/cluster.env` | The knob was not forwarded into the container, and the serve line also preferred a script-local alias variable over the forwarded value | The name is resolved once, on the host, so the profile's `SERVED_MODEL_NAME` is what the engine serves |
| The in-container gate printed a Python traceback instead of a clear failure line when the checkpoint directory was malformed | The gate read the checkpoint's config files without guarding the read | The gate reports its own `FAIL` line for a missing, unreadable, or non-object file, and for a missing model directory |
| The recipe's own "Served numbers" table claimed temp-0 determinism across runs, but no gate in the recipe could support that claim | The determinism gate used short prompts. The failure mode that matters for this model lives in the last chunk of a chunked prefill when that chunk runs as a piecewise CUDA graph, and a short prompt never reaches the chunked-prefill boundary | The claim now says what it covers, and a second gate (long-prompt determinism) builds a prompt of exactly `max_num_batched_tokens + 10` tokens and compares the generated token sequence across one cold run and two prefix-cached runs, with the decode logprobs compared against a tolerance |
| `BLOCK_SIZE=256` looked ignored: `/metrics` reported `block_size = 128` | `/metrics` reports the **minimum** block size across the prefix-cacheable KV groups, and this model's sliding-window group is 128. The requested value is the scheduler block size, which the engine logs as the LCM (256) | The README explains where 256 comes from (the sparse-SWA backend's own preferred size on this hardware), and the acceptance gate checks the requested value, the LCM the engine logs, and the metric label |
| The resolved-backends gate would have failed on a healthy lane for the wrong reason | Two of its log markers were written against a log format this engine does not emit: the chunked-prefill boundary is logged as `max_num_batched_tokens=8192`, and the attention backend has no single "Using … backend" line at all | Both markers now match lines the engine actually prints, read off a real startup log, and the file that prints each one is hash-pinned in the engine-identity manifest so the format cannot change under the gate |
| The resolved-backends gate compared the attention backend against nothing | The marker was a bare substring with no value in it, so the expected backend was never compared to anything: any attention backend, or none, passed | The marker is now value-bearing — it interpolates the expected backend — and a second check asserts the TP=3 head padding the fork performs, which is the recipe's whole reason for existing |
| A renamed key in the engine-identity manifest silently disabled its own check | Each expectation was looked up by name, and a name that no longer matched was skipped as "not configured" | The gate now fails when a manifest expectation is not covered by any check, so renaming a key is a loud failure instead of a silent no-op |
| The forbidden-MoE-backend marker would have matched a healthy lane | Its fallback marker was the bare family name, and the engine's all-reduce dispatch prints the quoted names `B12X_PCIE` and `B12X_ROCENANTE` in the same log | The marker is the prefix of the MoE enum name only, which covers both MoE variants and cannot match the transport backends (that b12x forbid was later retired when b12x became the shipped default — failure mode 14 — and the clamp hazard moved to the tiny-decode env check) |
| The long-prompt gate could not land on an exact token count | It binary-searched over characters for a prefix of the right length, but byte-level BPE counts are not monotonic in the prefix length — a longer prefix can tokenize into fewer tokens — so the search had no correctness guarantee and the walk that followed it burned round trips | The prompt is built from token IDs taken from the engine's own tokenizer and sent as those IDs, so the count is exact by construction, and the engine's own prompt count is asserted afterwards |
| The long-prompt gate cited a logprob bug it never checked | It compared token IDs only; at temperature 0 a logprob shift need not change the argmax token, so a lane with the prefix-cache replay drift could still pass | The decode logprobs are captured and compared between the cold and the cached runs, within a tolerance, and the measured drift is printed on every run |
| The long-prompt gate could compare two cached runs and call it a cold one | A repeat run found its own prompt already in the prefix cache, so the cold-against-cached comparison quietly stopped testing anything | A fresh nonce is put at the head of the prompt on every run, so the first call is genuinely cold |
| `stage-env` did not copy the two new gate scripts to the boxes | The staging step copied only the boot gate and the identity manifest, so the gates a reader is told to run were not on the box | The staging step copies the whole kit |
| Nothing proved the engine had resolved the kernels the recipe was validated against | The MoE backend, the dense-linear kernel and the attention backend are chosen by the engine's own policy, not by the flags in the config file, so a newer image could change them silently | The engine-identity manifest now pins the files that make those choices and the model-side values they consume, and a new gate checks what the engine actually resolved — including the tiny-decode kill switch that keeps the b12x MoE carrying the model's clamped-SwiGLU limit (the tiny-decode path drops it — see failure mode 14) |
| The comparison table carried other people's numbers that no one had checked, and two of them were wrong | The figures were copied from earlier reading without going back to the source repositories, and one row named a repository that does not exist | Every figure is now read from the linked repository, and the row with no source is gone. The table says plainly that the other rows are other people's published numbers, not measurements |
| The acceptance gate said it checked the requested block size, and it did not | It checked the LCM the engine logs and the metric label — but neither is what the command line asked for, so a flag that was read and never forwarded would have passed | The gate now reads the requested value from the container's **environment**, where the launcher forwards it (`-e BLOCK_SIZE=`), and falls back to the command line only for a literal number. The command line alone cannot carry it: the serve line is a shell string, so it holds the literal `"${BLOCK_SIZE:-256}"` — identical text for every value, which would have made the check unable to fail |
| The launcher carried a second served-name knob that nothing read | `SERVED_NAME` was a leftover from the pre-fork launcher, where it was one of TWO served names. The fork launcher serves a single name from `SERVED_MODEL_NAME` (README wall 5), but `SERVED_NAME` was still defined and still forwarded into the container — where the bootstrap never reads it. A reader who set it would see no effect, and its default (`deepseek-v4.1-flash`) reads like a second served name that does not exist | The dead knob is gone. The engine serves exactly the one name the profile sets, and the bootstrap's `--served-model-name` is driven by the variable that is actually forwarded |
| The gate's own command was written for a place it cannot run in | The gate reads the local container, so it cannot be run from a checkout against a remote box, and the path it named does not exist on the box either | The validation document says which gates run where, and gives the on-box invocation |
| The recipe set the RoCE all-reduce knob and nothing checked whether it fired | The launcher sets `VLLM_ENABLE_ROCE_ALLREDUCE=1`, but the one-shot RoCE collective needs both RoCE rails of a link, and the shipped topology has one cable per pair of boxes (three cables, each device connected to the other two, both of each device's ports in use) — so the engine logs a failure and falls through to `PYNCCL`, silently. The knob was set, the collective was absent, and the reduction was carried by a different path with no error signal | The expectation now lives in the engine-identity manifest and the gate asserts the transport that actually engaged, on every group the engine reports. On the shipped topology the expected value is `PYNCCL`; a reader who adds a second cable between the same pair of boxes gets a FAIL until they update the expectation, so the fabric change is a gated event rather than an unrecorded one |
| The new all-reduce check compared the engine's quoted list against a bare name | The engine prints the engaged backends as a Python list repr (`Using ['PYNCCL'] all-reduce backends`), so the captured text carries the quotes and never matched the manifest's bare name — the check would have failed a perfectly healthy lane | Both sides are normalised to bare names before the comparison, so a name that differs only by quoting is the same backend |
| The new all-reduce check read only the first dispatch line | The engine prints one dispatch line per group (the TP group and the EP group) and the groups are independent, so a lane that engaged the collective on one group and fell back on the other would have passed | Every dispatch line the engine printed is checked, and the failure names the ones that disagree |
| The manifest claimed every marker emitter was hash-pinned, and four of the files it meant were not | The all-reduce transport marker is read from the engine's own dispatch line, emitted by `vllm/distributed/device_communicators/cuda_communicator.py`, which was not in the pinned set; the attention-backend marker is read from the b12x readiness line, whose format lives in `flashinfer/experimental/b12x/preparation/_progress.py` and whose `attention.dsa_indexer` name comes from the op registry in `flashinfer/experimental/b12x/_api.py`; and the **forbidden** `NvFp4 MoE backend` marker is emitted by exactly one file, `vllm/model_executor/layers/fused_moe/oracle/nvfp4.py`, which was not pinned either. The protection the recipe advertises was therefore narrower than the recipe said | All four are now pinned, with their hashes read from the running container of the pinned image. The claim is now true for every marker the post-boot verifier asserts — present or forbidden — and a drifted pin fails the boot gate |
| The vocabulary-divisibility section explained a mechanism the shipped build does not contain | It said the fork divides the raw vocabulary by the TP size and that the check requires `--served-model-name` to be set. No such check is in the pinned image: the only vocabulary-divisibility check is in the b12x ngram-embedding path, it divides a **padded** vocabulary, and it raises a `ValueError` with a different message. | The shipped launcher lacked an image-limit knob present in the validated configuration | The launcher bytes predated a knob added to the validated configuration | The launcher was regenerated with the knob; it is inert for this text-only model |

## Deferred items that were closed

Some questions survive a bring-up as a "try this later" list.
Two of them were closed during a later audit, and the reason is recorded
here so they are not carried forward again:

| Item | Why it was closed |
|---|---|
| Engram auto-prefetch | The engine's precondition is that the checkpoint fits inside 90% of the memory AVAILABLE AT LOAD TIME. Even on an idle box that is 90% of ~121 GiB of unified memory — ~109 GiB — and this model's checkpoint is well over it, on any filesystem. The posture this recipe already runs (`--engram-config '{"cpu_offload":false,"table_memory":"disk"}'`) is the answer. The open question is not the prefetch but whether a smaller checkpoint exists |
| A wider chunked-prefill batch width | Raising `MAX_NUM_BATCHED_TOKENS` to 16384 killed both worker ranks during the compile phase (row 9 above). More compile workers is not the fix — it increases the very memory spike that killed them — and a persistent compile cache is a lane experiment, not a desk change |
