# FIXLOG — ds41-flash-tp3 (V4.1-Flash on 3× DGX Spark, vLLM b12x)

Every failure mode encountered during bring-up, its root cause, and its
fix. Roughly ordered by when each failure was met on the road to first light (boot-fatal modes first).

| # | Symptom | Root cause | Fix |
|---|---|---|---|
| 1 | Head node kernel-OOM during weight load; workers survive | NCCL connection buffers pin ~4.7 GiB unreclaimable host RAM per node; the head (carrying the API server and the usual daemons) has ~2 GiB less margin than workers | `NCCL_BUFFSIZE=1048576`, `NCCL_LL128_BUFFSIZE=262144`, `NCCL_PROTO="^LL128"` — cuts pinned to 139 MiB |
| 2 | Kernel-OOM ~7 s into load with only 1.4 GiB process RSS | Engram tables staged into host memory (~31 GiB/rank) on top of 95 GiB weights | `--engram-config '{"cpu_offload":false,"table_memory":"disk"}'` |
| 3 | Head node OOM at ~4 min into load (repeats identically across 4 boots) | The b12x O_DIRECT loader's pinned bounce buffers add 10–16 GiB unreclaimable host memory during weight loading | `--load-format safetensors` (kernel-evictable page cache instead of pinned buffers) |
| 4 | `ValueError: Free memory on device cuda:0 less than desired GPU memory utilization` | The fork checks free memory at startup against gmu × total; busy head node has less free than clean workers | gmu 0.85 (not the fork default 0.92); run `echo 3 > /proc/sys/vm/drop_caches` before boot |
| 5 | `io_uring bounce initialization failed: Operation not permitted` | Docker's default seccomp profile blocks io_uring syscalls used by the b12x I/O layer | `--security-opt seccomp=unconfined` |
| 6 | `AssertionError: 129280 is not divisible by 3` | The fork divides raw vocabulary by TP size; V4.1's vocab (129,280) is not divisible by 3 | Use a single `--served-model-name main` (the alias path); the fork runtime-pads attention heads, o_groups, and drafter experts automatically |
| 7 | Spec decode (DSpark k=5) boot OOMs at every gmu/KV combination | Draft model adds ~3 GiB/rank; at TP3 there is no room for both the draft and a meaningful KV pool | Rejected on capacity; documented as the speed/capacity trade |
| 8 | `expandable_segments:True` produces NaN logits on >64-token prompts | GB10 unified memory + PyTorch's expandable segments allocator interact badly | `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False` (mandatory) |
| 9 | Raising the chunked-prefill batch width to 16384 killed BOTH worker ranks during the b12x compile phase, while the head node's worker survived — the lane came back healthy only after reverting to 8192 | Larger batch shapes create new b12x compile candidates, and the compile-time memory spike exhausts unified memory on the workers before any serve-time memory check runs; the startup free-memory gate evaluates a config-time snapshot and does not cover compile shapes. The kernel log on a dead worker shows the generic signature: `Out of memory: Killed process ... (VLLM::Worker_TP)` followed by an NVIDIA `NV_ERR_NO_MEMORY` from the unified-memory allocator | Keep the shipped 8192 — the launcher's `MAX_NUM_BATCHED_TOKENS`/`MNBT` knob carries this warning inline. A retest requires a memory plan: reduced `GMU` for the boot window, a post-weight-load available-RAM check on every box (the config-time snapshot is not the serve-time state), and the b12x reader's own block counters surfaced so the effect is measured. Forensics note: plain `dmesg` is permission-denied on these boxes — `sudo -n dmesg -T` works, and its stamps are the box's LOCAL time, not UTC, so kernel timestamps and engine logs disagree by the box's UTC offset |

## Failures in the bring-up path itself

These are defects in the recipe's own scripts, not in the serving stack —
they were found by re-running the published quick start end to end. If
you are on an older copy, expect them.

| Symptom | Root cause | Fix |
|---|---|---|
| `./launch/ds41-flash-tp3-up: Permission denied` | The launcher was published without the executable bit, so the quick start could not start | Published with mode 755 |
| `preflight failed on <box>` on the first box, every time, with `MISSING: checkpoint not staged` | The checkpoint check expanded `$(source "$ENV_SRC" ...)` on the BOX, where `ENV_SRC` is unset, so the path was empty and the test could never pass | Resolve every value on the operator's side, inject it as a literal, and let the box use its own variables |
| `preflight` never warned about memory | The `free -g | awk` field reference was written `$$7` inside a double-quoted ssh payload, so `$$` expanded to the operator's shell PID on the sending side and the box received a literal `PID7` instead of `$7` — the comparison never matched | `\$7`, so the box compares field 7 |
| `preflight` accepted any image named `eugr/spark-vllm-b12x:nightly-20261015` | The check compared the tag string only; a moved tag passes | The preflight now asserts the manifest digest AND the sha256 of the image's RootFS layer list |
| `start` failed with `bash: start-tp3-fork.sh: No such file or directory` | The launcher called a script the recipe did not ship, and `stage-env` copied only `cluster.env` | The recipe now ships `launch/start-tp3-fork.sh` and `launch/tp3-kit/`, and `stage-env` copies both to every box |
| `stage-env` failed with `No such file or directory` | The remote target directory was never created | `stage-env` creates the layout on each box first |
| Edits to `config/cluster.env` (KV pool, block size, max-num-seqs, parsers, loader) were silently ignored, and the served line did not match the file | The launcher never forwarded those knobs into the container, so the engine always ran the built-in defaults | The knobs are forwarded into the container explicitly, and the served line can be read straight off the command the launcher runs |
| The engram configuration in `config/cluster.env` had no effect, and the value the launcher held could pick up a stray `}` once it was actually passed through | The value was never forwarded into the container, and its default sat inside a `${VAR:-...}` expansion — where a `}` ends the expansion early as soon as the variable is set, so the value was correct only while nothing set it | The default is assigned in two steps with a single-quoted literal, on the host side and again inside the container, so the profile's value is passed through unchanged |
| `RAM-PROBE FINAL min_available_kb=0` on a box with several GiB free | The probe sampled `MemAvailable`, which reports 0 on this unified-memory kernel even when memory is available | The probe measures reclaimable headroom instead (free + reclaimable slab + reclaimable page cache) and keeps the minimum across the boot; `MemAvailable` is still reported beside it so the discrepancy stays visible |
| The served model name stayed `main` even after `SERVED_MODEL_NAME` was changed in `config/cluster.env` | The knob was not forwarded into the container, and the serve line also preferred a script-local alias variable over the forwarded value | The name is resolved once, on the host, so the profile's `SERVED_MODEL_NAME` is what the engine serves |
| The in-container gate printed a Python traceback instead of a clear failure line when the checkpoint directory was malformed | The gate read the checkpoint's config files without guarding the read | The gate reports its own `FAIL` line for a missing, unreadable, or non-object file, and for a missing model directory |
| The recipe's own "Served numbers" table claimed temp-0 determinism across runs, but no gate in the recipe could support that claim | The determinism gate used short prompts. The failure mode that matters for this model lives in the last chunk of a chunked prefill when that chunk runs as a piecewise CUDA graph, and a short prompt never reaches the chunked-prefill boundary | The claim now says what it covers, and a second gate (long-prompt determinism) builds a prompt of exactly `max_num_batched_tokens + 10` tokens and compares the generated token sequence across one cold run and two prefix-cached runs, with the decode logprobs compared against a tolerance |
| `BLOCK_SIZE=256` looked ignored: `/metrics` reported `block_size = 128` | `/metrics` reports the **minimum** block size across the prefix-cacheable KV groups, and this model's sliding-window group is 128. The requested value is the scheduler block size, which the engine logs as the LCM (256) | The README explains where 256 comes from (the sparse-SWA backend's own preferred size on this hardware), and the acceptance gate checks the requested value, the LCM the engine logs, and the metric label |
| The resolved-backends gate would have failed on a healthy lane for the wrong reason | Two of its log markers were written against a log format this engine does not emit: the chunked-prefill boundary is logged as `max_num_batched_tokens=8192`, and the attention backend has no single "Using … backend" line at all | Both markers now match lines the engine actually prints, read off a real startup log, and the file that prints each one is hash-pinned in the engine-identity manifest so the format cannot change under the gate |
| The resolved-backends gate compared the attention backend against nothing | The marker was a bare substring with no value in it, so the expected backend was never compared to anything: any attention backend, or none, passed | The marker is now value-bearing — it interpolates the expected backend — and a second check asserts the TP=3 head padding the fork performs, which is the recipe's whole reason for existing |
| A renamed key in the engine-identity manifest silently disabled its own check | Each expectation was looked up by name, and a name that no longer matched was skipped as "not configured" | The gate now fails when a manifest expectation is not covered by any check, so renaming a key is a loud failure instead of a silent no-op |
| The forbidden-MoE-backend marker would have matched a healthy lane | Its fallback marker was the bare family name, and the engine's all-reduce dispatch prints the quoted names `B12X_PCIE` and `B12X_ROCENANTE` in the same log | The marker is the prefix of the MoE enum name only, which covers both MoE variants and cannot match the transport backends |
| The long-prompt gate could not land on an exact token count | It binary-searched over characters for a prefix of the right length, but byte-level BPE counts are not monotonic in the prefix length — a longer prefix can tokenize into fewer tokens — so the search had no correctness guarantee and the walk that followed it burned round trips | The prompt is built from token IDs taken from the engine's own tokenizer and sent as those IDs, so the count is exact by construction, and the engine's own prompt count is asserted afterwards |
| The long-prompt gate cited a logprob bug it never checked | It compared token IDs only; at temperature 0 a logprob shift need not change the argmax token, so a lane with the prefix-cache replay drift could still pass | The decode logprobs are captured and compared between the cold and the cached runs, within a tolerance, and the measured drift is printed on every run |
| The long-prompt gate could compare two cached runs and call it a cold one | A repeat run found its own prompt already in the prefix cache, so the cold-against-cached comparison quietly stopped testing anything | A fresh nonce is put at the head of the prompt on every run, so the first call is genuinely cold |
| `stage-env` did not copy the two new gate scripts to the boxes | The staging step copied only the boot gate and the identity manifest, so the gates a reader is told to run were not on the box | The staging step copies the whole kit |
| Nothing proved the engine had resolved the kernels the recipe was validated against | The MoE backend, the dense-linear kernel and the attention backend are chosen by the engine's own policy, not by the flags in the config file, so a newer image could change them silently | The engine-identity manifest now pins the files that make those choices and the model-side values they consume, and a new gate checks what the engine actually resolved — including that the MoE backend is not the b12x one, which would silently drop the model's clamped-SwiGLU limit on small-batch decode |
| The comparison table carried other people's numbers that no one had checked, and two of them were wrong | The figures were copied from earlier reading without going back to the source repositories, and one row named a repository that does not exist | Every figure is now read from the linked repository, and the row with no source is gone. The table says plainly that the other rows are other people's published numbers, not measurements |
| The acceptance gate said it checked the requested block size, and it did not | It checked the LCM the engine logs and the metric label — but neither is what the command line asked for, so a flag that was read and never forwarded would have passed | The gate now reads the requested value from the container's **environment**, where the launcher forwards it (`-e BLOCK_SIZE=`), and falls back to the command line only for a literal number. The command line alone cannot carry it: the serve line is a shell string, so it holds the literal `"${BLOCK_SIZE:-256}"` — identical text for every value, which would have made the check unable to fail |
| The gate's own command was written for a place it cannot run in | The gate reads the local container, so it cannot be run from a checkout against a remote box, and the path it named does not exist on the box either | The validation document says which gates run where, and gives the on-box invocation |
